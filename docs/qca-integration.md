# PawsPawns 集成 QCA（Qoder Cloud Agents）方案

## 一、两轮思考

**第一轮**列出六个候选：赛后复盘教练、实时对局旁白、自适应难度、每日谜题生成、引擎与开局库离线扩建、浏览器自动回归。

**第二轮**用两条硬约束筛除：

1. **QCA 是异步云端 Agent**，一次任务从秒级到分钟级，绝不能进入"玩家落子 → AI 回应"的主循环。所以"实时旁白"必须降级为**离线预烧台词 + 运行时查表**，命中不到就退回本地模板。
2. **凭据不能进前端**。所有调用必须经自建服务端代理（如 `/api/qca`），前端只拿结果 JSON；失败要有明确降级（`credential_required` / `rate_limited` / `transient`）。
3. 线上自动改写难度参数会让玩家困惑，也要求玩家数据落库，违背"少即是多"，因此改为**离线标定、人工审核后随版本发布**。

## 二、三个方案

### 方案 A：赛后「动物教练」复盘卡（推荐先做）

对局结束后把 PGN + 难度档位提交给 QCA，异步产出一张复盘卡：3 个关键转折点、每处一句拟人化点评（狮王长老口吻）、一条下次建议。前端在结算页显示"教练正在看你的棋…"，轮询到结果再展开；超时就只显示本地统计。

- **价值**：把一局弃子变成一次学习，是最直接的可玩性增量；异步天生契合 QCA。
- **成本**：一个代理路由 + 结算页一个卡片组件，不动引擎。
- **风险**：点评可能出现事实性错误。缓解：关键点由本地引擎给出评分差，QCA 只负责措辞，不负责判断棋力。

### 方案 B：每日谜题工坊

用 QCA 定期离线扫描玩家败局（或引擎自对弈局），生成"救援谜题"：一个残局 FEN、一步或两步的最佳解、一段动物剧情文案，产出为静态 JSON 随构建发布。

- **价值**：给这款一次性对局游戏补上留存内容，且不增加运行时延迟。
- **成本**：谜题数据格式 + 一个新的谜题模式页面（复用现有棋盘与点击落子）。
- **风险**：谜题唯一解需校验。缓解：生成后用本地引擎逐题验证，不通过就丢弃。

### 方案 C：引擎与难度实验室（价值最高）

让 QCA 作为开发期 Agent 做四件离线工作：把仅 7 条的开局库扩到数百条；为 `search.ts` 加迭代深化、置换表、静态搜索节点上限；用客观引擎批量标定三档的平均失误值（ACPL）并给出参数建议；批量预烧方案 A 的台词模板。

- **价值**：直接修掉实测出的硬伤——Lv2 中局单步 14~16 秒、Lv3 单步 77 秒、三档着法质量几乎无差别。
- **成本**：不改产品形态，改动集中在引擎与数据文件，可分批合入。
- **风险**：引擎改动可能引入错误着法。缓解：以基准脚本为验收门槛，回归不过不合。

**备选 D**：用 QCA 的浏览器工具集跑自动回归，每次发布前自动走完一局并截图比对，守住点击落子等交互不被改坏。

## 三、共同架构红线

统一走 `服务端代理 → 提交任务 → 轮询 → 落地为静态资源或结算页 JSON`。QCA 只做"离线增值"与"赛后解释"，落子决策永远留在本地 Web Worker，保证断网可玩、单步零等待。

## 四、推荐顺序

**C → A → B**。先用 C 把等待时间和难度区分度修好（这是当前最伤体验的问题），再用 A 增加对局后的获得感，最后用 B 扩内容。
